Overview

Omni fiesta is a single-room party game for about 15 players, built for one live event. One Node process serves an Express HTTP API, a Socket.IO channel and the built React client. All state lives in one SQLite file. There is no external queue, cache or second service, apart from an optional call to CoinGecko for market prices.

Three kinds of screens connect to a room:

ViewRouteWhoCan see
Player/playPhonesOwn balances and own choices, plus public game state
Host/hostOne private laptop or phoneEverything, including emails, phones, all balances and the ledger
Display/screenTV, a fixed 1920×1080 stage scaled to fitPublic state only

The central design rule is that the server decides everything. Clients send intent (a command) and receive a complete, role-filtered snapshot of the room. They never compute outcomes, balances or deadlines.

Runtime topology

  • One writer. node:sqlite is synchronous, so every command runs to completion inside one BEGIN IMMEDIATE transaction. Two simultaneous commands cannot interleave.
  • Pull then push. Commands arrive over HTTP (POST /api/rooms/:code/commands). Results are pushed to every connected socket as a fresh snapshot, so a phone that reconnects only has to ask for state once.
  • No background jobs. The only timer is a 250 ms ticker that closes rounds whose deadline has passed and triggers a broadcast.

Stage state machine

A room is always in exactly one stage (rooms.phase) with a status of pending, open or closed. Each time the host advances, phase_instance increments by one. Per-stage data is keyed by (room_id, phase_instance), which also lets stale commands from an old screen be rejected.

  • Timed stages (investments, costume, slots, powerball) open as pending. The host's phase.start sets opened_at and deadline_at in server time. A retried start never extends the deadline. Untimed stages open immediately as open.
  • Closing: the ticker (or phase.close) sets status='closed' and calls the module's close hook inside the same transaction.
  • Advance rules are in Engine.advanceBlocker: the round must be closed, opening prices must exist before investments, locked and reserved balances must be zero before the finish, and the module's assertCanAdvance must pass. The same function feeds canAdvance and advanceBlocker in snapshots so the host UI explains why Next is disabled.

The command pipeline

Every state change is one Command posted by an authenticated session. Engine.execute handles all of them.

POST /api/rooms/:code/commands  { requestId, phaseInstance, type, payload }

execute(session, roomId, command)
  1. authorize: host, or a player of this room
  2. expire(roomId)                       persist any passed deadline first
  3. BEGIN IMMEDIATE
  4.   store.once(scope, requestId, command, () => {   idempotency envelope
  5.     check command.phaseInstance == room.phase_instance   else STALE_PHASE
  6.     dispatch by type:
           player.ready | phase.advance | phase.start | phase.close
           phase.host   -> host action for the current stage
           phase.action -> module.action(player, action, data)
  7.     store.bump(roomId)                version++ so clients can order snapshots
  8.   })
  9. COMMIT  (any thrown GameError rolls everything back)
 10. app.ts broadcasts a fresh snapshot to every socket in the room
CommandWhoEffect
player.readyPlayerLobby ready flag
phase.advanceHostMoves to the next stage after the blocker checks
phase.startHostOpens a pending timed round and starts its clock
phase.closeHostCloses the round early
phase.hostHostStage-specific host action, for example lock, next, draw, settle, refund. Dispatched by phase in engine.ts
phase.actionPlayerA game input, for example vote, invest, spin, bet. Rejected unless the round is open and before its deadline
Why this shape? Putting authorization, deadlines, idempotency and persistence in one pipeline means a game module only has to describe rules. It cannot forget to check the clock or double-apply a retry.

Accounting and idempotency

Request idempotency

Store.once stores the fingerprint (hash of the command) and the JSON result in operations, keyed by (scope, request_id). A network retry with the same requestId and the same body returns the saved result without running again. The same ID with a different body fails with REQUEST_CONFLICT. The client reuses its request ID after a network error and sends one command at a time.

The token ledger

Each player has three balances on the players row, all with CHECK(>=0):

BalanceMeaning
spendableFree to use for slots, bets and the final ranking
lockedPrincipal tied up in investments until settlement
reservedPowerball bets held until the draw

The only code that changes a balance is Store.adjust(roomId, playerId, operationKey, reason, delta, now). It writes a ledger row and updates the player in the caller's transaction. UNIQUE(player_id, operation_key) makes each effect idempotent: replaying the same key with the same delta and reason is a no-op, and replaying it with a different delta or reason raises REQUEST_CONFLICT. A change that would make any balance negative raises INSUFFICIENT_FUNDS.

Operation key patternUsed for
investment-settlement:<asset>Settling or refunding one position (shared on purpose, so settle and refund are mutually exclusive)
costume:<instance>One costume prize or penalty per player
per-request keysSlot spins, powerball bets, trivia awards and similar

Game modules never write balances directly. The ledger also doubles as an audit trail: the host view shows the latest 100 entries.

Game modules

Each game implements the small PhaseModule interface from core/phases.ts and is registered once in src/server/games/index.ts (createPartyModules).

interface PhaseModule {
  id: Stage;
  durationSeconds(config): number | null;  // null = untimed stage
  open?(context): void;                    // after the stage becomes current
  action(context, playerId, action, data): Record<string, unknown>;  // player input
  close?(context): void;                   // when the round closes
  assertCanAdvance?(context): void;        // throw GameError to block "Next"
}
// context = { store, room, config (frozen at room creation), now, requestId }

Host-only actions are plain functions (for example costumeHostAction, powerballHostAction) called from the phase.host branch of engine.ts. Projections are also plain functions that return the per-role view for a stage (for example costumeProjection(context, role, playerId)), so the module decides what each role may see.

ModuleNotes
investments / investmentReviewPicks lock principal. Review settles once from a closing snapshot, or the host can refund every stake at cost if closing prices cannot be loaded. Payout math is exact integer arithmetic (investment-math.ts, BigInt, floor)
costume / costumeRevealVoting with tie re-votes, a host lock, then a separate reveal stage near the end. See reveals
triviaBalanced teams, a buzzer window, host judging, per-teammate awards with receipts and undo
slotsPaid spins, one saved result per attempt, server-side randomness
powerballRed or blue pool betting. Bets reserve tokens; draw then reveal settles once
somebody-callingOne private random player draw; the host calls manually, then reveals

Production randomness uses server-side cryptographic randomness. Tests inject fixed random sources and fake clocks.

Real-time state and role projections

Clients do not receive diffs. After any change, app.ts builds one snapshot per connected viewer with Engine.snapshots(viewers) and emits it as state. Broadcasts are coalesced on a 16 ms timer, so a burst of commands produces one push. Snapshots carry a snapshotSequence and the room version; the client ignores older snapshots that arrive out of order.

Shared data is read once, then projected for each role:

Snapshot fieldPlayerHostDisplay
room, players (name, emoji, ready, connected)yesyesyes

Because the server filters per viewer, privacy does not depend on the client hiding fields. Tests assert that emails and phone numbers never appear in player or display payloads.

Clock and reconnects

The client measures its offset from server time (/api/time and the clock socket event) and renders countdowns from deadlineAt. Reconnecting just calls sync and receives a full snapshot, so there is no replay logic.

Sessions and authorization

  • Host: POST /api/login with the host password (at least 12 characters, from the environment). Compared with timingSafeEqual on hashes, rate limited to 10 attempts per minute per IP.
  • Players: join with a room code, a profile and a joinKey. The join is idempotent (joins table), so a double tap cannot create two players.
  • Display: a long random display token is shown once as a TV link. Only its hash is stored (rooms.display_token_hash). Creating a new link replaces the old one.
  • Cookies: opaque random tokens, httpOnly and sameSite=strict. The database stores only token hashes (sessions.token_hash).
  • Recovery: the host can issue a short-lived recovery link for a player who lost a session (recovery_tokens, recovery_receipts).
  • Sockets: authenticate with the same cookie or display token and re-authorize on every push. A revoked or expired session is disconnected.

Market data and investments

  1. The host prepares opening prices before the investment stage (POST /api/rooms/:code/market/opening). This calls CoinGecko once, validates freshness and spread against config, and saves one row in market_snapshots.
  2. Players pick assets and amounts. Principal moves spendable → locked by ledger entry.
  3. At the closing bell the host prepares closing prices the same way. Settle computes each payout from opening and closing price and the configured multiplier, bounded so a loss never exceeds principal, and releases locked by ledger entry.
  4. If closing prices cannot be loaded, the host can refund instead. It returns each principal in full under the same operation key as settlement. It is refused once a closing snapshot exists, and closing preparation is refused after a refund.

A room created in fixture mode (room_market_modes) uses deterministic fixture prices for rehearsals. Prices are never synthesized in a live room.

Step-by-step reveals

Two moments are announced one place per host click: the costume winners and the final ranking. Both follow the same pattern: compute everything up front, reveal progressively, and filter by progress when projecting.

Costume

  1. During the costume stage the host closes voting and locks (costume_locks). Locking calculates places into costume_results but moves no tokens. A tie for first must be settled by re-vote first (costume_rounds).
  2. The costume-reveal stage comes after Somebody's calling. Each next click reads costume_reveal_progress.step and announces the next group: 3rd, 2nd, last place, then 1st. Ties share a step; empty places are skipped; under 3 players there is one step. One more click then shows the full list.
  3. Tokens move at each step for that group only, using costume:<instance>. The last-place penalty is recomputed against the balance at that moment and capped at spendable.
  4. Each click carries the step the host saw. A stale step is rejected (STALE_STEP), so a double tap cannot announce two places.

Final ranking

The ranking is always computed from balances. finish_reveal_progress.step controls how much a non-host viewer receives (publicRanking in finish-reveal.ts): ranks 3, 2 and 1 in turn, then everyone. The host always receives the full list plus rankingStep and rankingSteps.

Configuration

config/game.yaml owns every adjustable value: timers, starting tokens, assets, investment cap and multiplier, costume prizes and penalty pool, slot odds, powerball settings and freshness limits for market data. It is validated with Zod at startup (src/server/config.ts), including cross-field rules such as costume prizes for exactly places 1 to 3.

The validated config is copied as JSON into rooms.config (with config_hash) when a room is created. A running party is not affected by later edits to the file, so change settings before creating the room.

SQLite data model

The database runs in WAL mode with foreign_keys=ON and a 5 second busy timeout. Timestamps are integer epoch milliseconds in server time. PRAGMA user_version is the schema version (currently 13).

Invariants enforced by the schema

  • Balances cannot go negative (CHECK on players, plus a pre-check in adjust).
  • A ledger effect applies once per player and key (UNIQUE(player_id, operation_key)).
  • One vote per voter per round, one bet per player per round, one investment per asset per player, one spin per attempt.
  • Player names are unique within a room, ignoring case.

Migrations

The store opens the file, reads PRAGMA user_version and runs each missing step inside its own BEGIN IMMEDIATE … COMMIT block, ending with PRAGMA user_version=N. Steps are additive where possible. Rebuilding a table (for example investments in v11 and costume_votes in v12) copies rows into a new table, drops the old one and renames. A database whose version is newer than the code refuses to start so an old build never writes to a newer schema.

VersionChange
2 to 4Market snapshots, room market mode, recovery tokens
5 to 7Costume, slots and trivia tables, Somebody's calling, Powerball
8 to 10Room archive, recovery receipts, trivia receipts
11investments keyed per asset (several assets per player)
12Costume rounds for tie-break re-votes
13Costume locks, costume reveal progress, final ranking reveal progress

Testing and rehearsal tools

  • npm test runs the Node test runner with tsx. Suites use in-memory SQLite, fake clocks, fixed market fixtures and injected randomness. They cover duplicate commands, simultaneous actions, deadline boundaries, insufficient funds, repeated settlement and per-role payload privacy.
  • npm run typecheck, npm run format:check and npm run build complete the check set.
  • scripts/fixture-server.ts starts a disposable, in-memory server with fixture prices. scripts/simulate.ts drives N simulated players (with --party, a full party through every stage) over the real HTTP and socket API.
  • scripts/preview-fixtures.ts seeds a room at a chosen stage for the preview gallery (just preview).
  • scripts/check-market.ts verifies live CoinGecko data before an event.
