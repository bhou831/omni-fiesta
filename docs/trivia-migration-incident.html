Omni Fiesta · incident note · October 30, 2026

Why the party server kept restarting

A database upgrade was skipped because two branches had assigned the same version number to different changes. When Trivia needed a missing table, the server crashed and restarted.

What this affected: active connections could drop whenever the server crashed. The stored party data was not intentionally erased. The fix is a normal, additive database migration; there is no need to create a new room to apply it.

What we observed

The Lightsail service logs showed repeated failures and a restart counter of 55. The full error named the missing table:

Error: no such table: trivia_adventures

The stack trace led from a timer-driven state broadcast to the Trivia state projection, which tried to read that table. A successful /api/health response only showed the server was alive at that moment; it did not exercise that database query.

How we diagnosed it

1. Identify the releaseThe installed revision was bf7134b, from the adventure feature branch.
2. Inspect the databaseRead-only checks showed schema version 16 and neither adventure table present.
3. Compare migrationsThe feature branch created those tables only when upgrading from a version below 15. Another branch had already used version 15 for a different ledger change.

The evidence matches a version collision: once a database said it was version 15 or later, the feature branch assumed its version-15 work had already run. Its version-16 update could then run without creating the adventure tables. The checks show the resulting state; they do not independently establish every earlier deployment step.

Why a version number matters

The app records a single database schema version. On startup it runs upgrades for versions the database has not yet reached. That works when each version represents the same change everywhere. Here, two branches independently gave different changes the same number:

HistoryVersion 15 meant
Main branchAdd a nullable reward marker to the ledger.
Adventure branchCreate tables for adventure state and item pools.

Knowing only “version 15” therefore did not tell the app which changes were actually present. An earlier feature revision had also used version 17, so the repair uses version 18.

The fix

Commit 9480781 adds a version-18 migration. It checks whether the ledger marker exists and adds it if needed; it also creates both adventure tables if missing. Existing tables and their contents are retained. The migration and version update run together in a database transaction.

When the updated app starts against the affected version-16 database, it should apply this repair automatically. The deployment script stops the service and creates a database backup before installing and starting the release. A future integration into main must preserve the repaired migration and schema version.

What was tested

Tests simulated both branch histories at versions 15, 16 and 17. They checked that the missing schema was added, existing adventure state was retained, and a room, player balance and ledger entry survived the migration and a restart. The full suite passed 146 tests with local port access; formatting, type checking and the production build also passed.

These are local test results. The fix was pushed to feature/adventure-trivia; a successful Lightsail deployment and live verification have not been independently observed here. After deployment, open the affected room and monitor the service logs for further errors.
